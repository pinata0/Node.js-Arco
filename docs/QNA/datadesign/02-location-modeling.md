# Location Modeling

## 문제

행사는 온라인 또는 오프라인으로 진행될 수 있으며, 오프라인 행사라면 장소 정보가 필요하다.

예를 들어 하나의 행사에는 다음과 같은 장소 정보가 포함될 수 있다.

- 장소명
- 주소
- 지역
- 위도
- 경도

이 장소 정보를 `events` 테이블에 직접 저장할지, 별도의 `locations` 테이블로 분리할지 결정해야 한다.

---

## 고려한 방식

### 1. `events` 테이블에 장소 정보를 직접 저장

예:

```text
events
├── id
├── title
├── venue_name
├── address
├── region
├── latitude
└── longitude
```

#### 장점

- 구조가 단순하다.
- 행사 조회 시 별도의 JOIN이 필요하지 않다.
- MVP 구현이 빠르다.
- 행사 데이터 입력과 수정이 직관적이다.

#### 단점

- 동일한 장소에서 여러 행사가 열릴 경우 장소 정보가 반복 저장된다.
- 같은 장소의 주소나 이름이 행사마다 다르게 입력될 수 있다.
- 장소 정보를 일괄 수정하기 어렵다.
- 향후 장소 자체를 검색하거나 관리하는 기능을 만들기 어렵다.

---

### 2. 별도의 `locations` 테이블로 분리

예:

```text
events
├── id
├── title
└── location_id

locations
├── id
├── name
├── address
├── region
├── latitude
└── longitude
```

관계는 다음과 같다.

```text
locations
    1
    │
    │
    N
  events
```

하나의 장소에서 여러 행사가 열릴 수 있으므로 `locations : events = 1:N` 관계가 된다.

#### 장점

- 동일한 장소 정보를 여러 행사에서 재사용할 수 있다.
- 장소 이름과 주소를 일관되게 관리할 수 있다.
- 장소 정보 수정 시 한 곳만 수정하면 된다.
- 위도·경도 등 장소 관련 속성을 확장하기 쉽다.
- 향후 장소 기반 검색이나 추천 기능을 구현하기 쉽다.

#### 단점

- `locations` 테이블이 추가된다.
- 행사와 장소를 함께 조회하려면 JOIN이 필요하다.
- 서로 다른 출처에서 같은 장소를 다르게 표기할 경우 동일 장소 판별 로직이 필요하다.
- 행사 수집 단계에서 장소 정규화 작업이 추가될 수 있다.

---

## 결정

**MVP에서는 장소 정보를 `events` 테이블에 직접 저장한다.**

별도의 `locations` 테이블은 현재 단계에서는 만들지 않는다.

예상 구조는 다음과 같다.

```text
events
├── id
├── title
├── venue_name
├── address
├── region
├── latitude
└── longitude
```

온라인 행사의 경우 장소 관련 컬럼은 `NULL`을 허용한다.

---

## 선택 이유

현재 MVP의 핵심 기능은 사용자가 날짜와 관심 분야를 입력했을 때 참석 가능한 행사를 찾는 것이다.

장소는 행사 검색에 필요한 정보이지만, 현재 요구사항에서는 장소 자체가 독립적인 핵심 엔티티는 아니다.

또한 초기 데이터는 여러 외부 출처에서 수집될 가능성이 높아 다음과 같은 표기 차이가 발생할 수 있다.

```text
COEX
코엑스
COEX Convention Center
서울 코엑스
```

이 단계에서 별도의 `locations` 테이블을 사용하면 이러한 값을 동일 장소로 식별하고 정규화하는 추가 로직이 필요하다.

MVP 규모에서는 이 복잡성이 얻는 이점보다 크다고 판단했다.

따라서 장소 정보는 우선 행사 자체의 속성으로 저장하고, 향후 동일 장소 데이터가 충분히 누적되거나 장소 기반 기능이 중요해질 경우 별도의 엔티티로 분리한다.

---

## 예상 컬럼

예를 들어 `events` 테이블에 다음과 같은 컬럼을 둘 수 있다.

```sql
venue_name VARCHAR(255),
address TEXT,
region VARCHAR(100),
latitude NUMERIC(9, 6),
longitude NUMERIC(9, 6)
```

각 컬럼의 역할은 다음과 같다.

| 컬럼 | 역할 |
|---|---|
| `venue_name` | 행사장 또는 건물 이름 |
| `address` | 상세 주소 |
| `region` | 서울, 부산, 광주 등 검색용 지역 |
| `latitude` | 지도 표시 및 거리 계산용 위도 |
| `longitude` | 지도 표시 및 거리 계산용 경도 |

위도와 경도는 데이터 출처에서 제공되지 않는 경우가 있으므로 `NULL`을 허용한다.

---

## 온라인 행사 처리

온라인 행사에서는 물리적 장소가 존재하지 않을 수 있다.

따라서 행사 진행 형태를 별도로 표현하고 장소 컬럼은 선택적으로 사용한다.

예:

```text
event_mode = ONLINE
venue_name = NULL
address = NULL
region = NULL
latitude = NULL
longitude = NULL
```

오프라인 행사라면 다음과 같이 저장할 수 있다.

```text
event_mode = OFFLINE
venue_name = "COEX"
address = "서울특별시 강남구 영동대로 513"
region = "서울"
```

온라인과 오프라인을 동시에 제공하는 하이브리드 행사는 별도의 `event_mode` 정책에서 다룬다.

---

## 향후 분리 기준

다음과 같은 요구가 생기면 `locations` 테이블로 분리하는 것을 다시 검토한다.

- 동일 행사장이 반복적으로 등장한다.
- 장소별 행사 조회 기능이 필요하다.
- 지도 기반 행사 탐색 기능이 중요해진다.
- 행사장별 상세 페이지가 필요하다.
- 장소의 위도·경도 및 주소를 중앙에서 관리할 필요가 생긴다.
- 동일 장소의 여러 표기를 정규화할 수 있는 데이터 또는 로직이 확보된다.

이 경우 다음과 같은 형태로 마이그레이션할 수 있다.

```text
locations
├── id
├── name
├── address
├── region
├── latitude
└── longitude

events
└── location_id → locations.id
```

---

## 결론

현재 MVP에서는 **장소를 독립적인 엔티티로 취급하지 않고 `events`의 속성으로 저장한다.**

이는 초기 데이터 수집과 구현을 단순하게 유지하기 위한 선택이며, 장소 재사용과 위치 기반 기능의 필요성이 커질 경우 `locations` 테이블로 분리한다.
