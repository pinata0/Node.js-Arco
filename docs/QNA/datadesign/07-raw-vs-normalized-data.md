# Raw vs Normalized Data

## 문제

행사 데이터는 외부 웹사이트나 API 등 여러 출처에서 수집될 수 있다.

수집한 원본 데이터에는 다음과 같은 문제가 포함될 수 있다.

- 필드 이름이 출처마다 다름
- 날짜/시간 형식이 다름
- 장소 표기가 일관되지 않음
- 태그 체계가 다름
- 일부 필드가 누락됨
- HTML이나 불필요한 문자열이 포함됨
- 동일 행사가 여러 출처에서 중복 수집될 수 있음

예를 들어 같은 의미의 데이터가 출처마다 다음처럼 들어올 수 있다.

```text id="y6g4v8"
startDate
start_time
event_start
date
```

또는 장소가 다음과 같이 표현될 수 있다.

```text id="5af2x1"
COEX
코엑스
서울 코엑스
COEX Convention Center
```

이러한 수집 원본을 서비스에서 사용하는 정제 데이터와 같은 구조에 바로 저장할지, 별도로 보존할지 결정해야 한다.

---

## 용어

이 문서에서는 두 종류의 데이터를 다음과 같이 구분한다.

### Raw Data

외부 출처에서 수집한 데이터를 가능한 한 원본 형태에 가깝게 보존한 데이터다.

예:

```json id="1p4o5e"
{
  "title": "[GIST] AI 세미나",
  "date": "2026.09.12",
  "time": "14:00",
  "place": "오룡관 101호",
  "category": "인공지능"
}
```

### Normalized Data

서비스 내부의 데이터 모델에 맞게 변환하고 정리한 데이터다.

예:

```text id="0d2nbb"
title       = "GIST AI 세미나"
start_at    = 2026-09-12T14:00:00+09:00
venue_name  = "오룡관 101호"
event_type  = "SEMINAR"
tag         = "AI"
```

---

## 고려한 방식

### 1. 수집 데이터를 바로 `events`에 저장

수집기가 외부 데이터를 읽은 뒤 즉시 서비스 스키마로 변환해서 저장하는 방식이다.

```text id="h8dyx7"
외부 데이터
    ↓
수집기
    ↓
정제
    ↓
events
```

#### 장점

- 구조가 단순하다.
- 별도의 raw 데이터 저장소가 필요하지 않다.
- 구현량이 적다.
- DB에 서비스에서 실제 사용하는 데이터만 존재한다.

#### 단점

- 정제 로직에 오류가 있으면 원래 데이터를 확인하기 어렵다.
- 파싱 규칙을 변경했을 때 기존 데이터를 다시 처리하기 어렵다.
- 어떤 값이 원래 출처에서 어떻게 제공되었는지 추적하기 어렵다.
- 데이터 품질 문제를 디버깅하기 어렵다.
- 수집기 수정 후 데이터를 다시 수집해야 할 수 있다.

---

### 2. 원본과 정제 데이터를 같은 테이블에 저장

예:

```text id="yiq4s9"
events
├── title
├── start_at
├── venue_name
├── raw_title
├── raw_date
├── raw_location
└── raw_data
```

또는 전체 원본을 JSON으로 저장할 수도 있다.

```sql id="v0a3b7"
raw_data JSONB
```

#### 장점

- 원본과 정제 결과를 한 행에서 확인할 수 있다.
- 구현이 비교적 간단하다.
- 원본 데이터 추적이 가능하다.

#### 단점

- `events` 테이블의 책임이 불명확해진다.
- 서비스용 필드와 수집용 필드가 섞인다.
- 출처별 raw 구조가 다르기 때문에 컬럼이 계속 늘어날 수 있다.
- 재수집 이력이나 여러 출처 데이터를 관리하기 어렵다.

---

### 3. Raw Data와 Normalized Data를 분리

원본 수집 데이터와 서비스에서 사용하는 행사 데이터를 별도로 관리한다.

예:

```text id="ab9x51"
raw_events
    ↓
정제 / 검증
    ↓
events
```

예상 구조:

```text id="u7mn3z"
raw_events
├── id
├── source
├── source_url
├── external_event_id
├── raw_data
└── collected_at

events
├── id
├── title
├── start_at
├── end_at
├── venue_name
└── ...
```

#### 장점

- 원본 데이터를 그대로 보존할 수 있다.
- 정제 로직이 바뀌어도 다시 처리할 수 있다.
- 데이터 변환 오류를 추적하기 쉽다.
- 수집 단계와 서비스 데이터 모델을 분리할 수 있다.
- 출처별 데이터 구조 차이가 `events`에 영향을 주지 않는다.
- 향후 자동 수집 파이프라인을 확장하기 쉽다.

#### 단점

- 테이블과 처리 단계가 늘어난다.
- 같은 데이터가 일부 중복 저장된다.
- raw → normalized 변환 로직이 필요하다.
- MVP 단계에서는 구조가 다소 복잡해질 수 있다.

---

## 결정

**수집 원본 데이터와 서비스용 정제 데이터를 분리한다.**

다음과 같은 흐름을 사용한다.

```text id="e4s2g0"
외부 출처
    ↓
수집
    ↓
raw_events
    ↓
정제 / 검증 / 중복 판별
    ↓
events
```

`raw_events`는 수집된 사실을 보존하는 역할을 하고, `events`는 서비스에서 실제 검색과 추천에 사용하는 정제된 데이터를 저장한다.

---

## 선택 이유

이 프로젝트에서는 향후 여러 출처에서 행사 데이터를 수집할 가능성이 높다.

출처가 늘어나면 각 사이트의 데이터 구조와 품질이 서로 다를 수밖에 없다.

이때 수집 데이터를 즉시 `events` 구조로 덮어써버리면, 정제 과정에서 문제가 발생했을 때 원인을 확인하기 어렵다.

예를 들어 다음과 같은 데이터가 수집되었다고 가정한다.

```text id="0znt6j"
원본
"2026.09.12 (토) 오후 2시"
```

정제 결과:

```text id="2k01qb"
start_at = 2026-09-12 02:00
```

실제로는 오후 2시, 즉 14시여야 하지만 파싱 오류로 02시가 저장되었다.

원본을 보존하지 않았다면 이 문제가 다음 중 어디에서 발생했는지 판단하기 어렵다.

```text id="5o9j6t"
원래 사이트의 오류
수집기의 오류
시간 파싱 로직의 오류
DB 저장 과정의 오류
```

반면 raw 데이터를 보존하면 원본과 정제 결과를 비교해 문제를 추적할 수 있다.

---

## Raw Data의 역할

`raw_events`는 서비스 사용자에게 직접 제공하는 데이터가 아니다.

다음 목적을 위해 사용한다.

- 수집 결과 보존
- 파싱 오류 디버깅
- 정제 로직 재실행
- 데이터 출처 추적
- 중복 판별 근거 확보
- 수집기 변경 전후 결과 비교

따라서 서비스의 일반적인 행사 검색 쿼리는 `raw_events`가 아니라 `events`를 대상으로 한다.

---

## Raw Data 저장 방식

출처마다 필드 구조가 다르므로 raw 데이터를 모든 출처에 공통된 관계형 컬럼으로 강제하지 않는다.

공통적으로 필요한 메타데이터만 별도 컬럼으로 저장하고, 출처 고유 데이터는 `JSONB`로 보존한다.

예:

```sql id="ps2lcn"
CREATE TABLE raw_events (
    id BIGSERIAL PRIMARY KEY,

    source VARCHAR(100) NOT NULL,
    source_url TEXT,
    external_event_id VARCHAR(255),

    raw_data JSONB NOT NULL,

    collected_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

예를 들어 `raw_data`에는 다음과 같은 데이터를 그대로 넣을 수 있다.

```json id="5yqvpf"
{
  "title": "AI Conference 2026",
  "schedule": "2026.09.12 14:00",
  "location": "서울 COEX",
  "topics": ["AI", "Data"],
  "registration": {
    "deadline": "09/10"
  }
}
```

---

## 서비스용 `events`

`events`에는 정제된 의미만 저장한다.

예:

```text id="1wq5sv"
events
├── id
├── title
├── event_type
├── start_at
├── end_at
├── venue_name
├── address
├── region
├── registration_deadline
└── ...
```

서비스는 이 테이블의 구조를 기준으로 동작한다.

따라서 수집 출처가 바뀌더라도 API나 추천 로직은 동일한 데이터 구조를 사용할 수 있다.

---

## Raw와 Normalized 데이터 연결

어떤 raw 데이터로부터 어떤 행사 데이터가 만들어졌는지 추적할 수 있어야 한다.

가장 단순한 방식은 `raw_events`에서 정제된 행사 ID를 참조하는 것이다.

예:

```sql id="bah1eo"
normalized_event_id BIGINT REFERENCES events(id)
```

또는 별도의 연결 테이블을 둘 수도 있다.

```text id="63cofs"
event_sources
├── event_id
└── raw_event_id
```

하나의 행사가 여러 출처에서 수집될 가능성이 있기 때문에 장기적으로는 연결 테이블 방식이 더 자연스러울 수 있다.

다만 이 구조는 `06-event-deduplication.md`의 중복 처리 방식과 함께 최종 DDL 단계에서 결정한다.

---

## 정제 과정

기본적인 처리 흐름은 다음과 같다.

```text id="jzx4kq"
1. 외부 데이터 수집

2. raw_events 저장

3. 필드 추출

4. 값 정규화
   - 제목 정리
   - 날짜/시간 변환
   - timezone 적용
   - 행사 종류 매핑
   - 태그 매핑
   - 장소 정보 정리

5. 데이터 검증

6. 중복 후보 확인

7. events 저장 또는 갱신
```

raw 데이터 저장은 가능한 한 정제 이전에 수행한다.

따라서 이후 단계에서 오류가 발생하더라도 수집한 원본 자체는 남는다.

---

## 정제 실패 데이터

일부 raw 데이터는 필요한 정보를 충분히 가지고 있지 않을 수 있다.

예:

```text id="xvl0nk"
제목은 존재
날짜 없음
```

또는:

```text id="u2v3dh"
날짜 문자열 파싱 실패
```

이러한 데이터를 억지로 `events`에 넣지 않는다.

대신 `raw_events`에는 보존하고 정제 실패 상태를 관리할 수 있다.

예:

```text id="5xkg7j"
PENDING
NORMALIZED
FAILED
```

필요하다면 다음과 같은 컬럼을 추가할 수 있다.

```sql id="5o64r9"
normalization_status VARCHAR(30),
normalization_error TEXT
```

현재 수동 데이터 구축 중심의 초기 MVP에서는 반드시 필요한 필드는 아니며, 자동 수집 파이프라인을 구현할 때 추가한다.

---

## 데이터 수정 원칙

`raw_events.raw_data`는 가능하면 수집 당시 상태를 유지한다.

원본 데이터에 문제가 있더라도 raw 데이터를 직접 수정해 정답을 만드는 방식은 사용하지 않는다.

대신 정제된 `events` 데이터를 수정하거나 정제 로직을 변경한다.

즉:

```text id="6a5eih"
raw_events
→ 수집 당시 기록

events
→ 현재 서비스에서 사용하는 해석 결과
```

이 구분을 유지한다.

---

## 저장 공간 문제

Raw와 Normalized 데이터를 모두 저장하면 일부 데이터가 중복된다.

하지만 MVP에서 계획된 데이터 규모는 크지 않으며, 텍스트 중심 행사 데이터이므로 저장 공간보다 다음 이점이 더 크다고 판단한다.

- 재처리 가능성
- 디버깅 가능성
- 데이터 출처 추적
- 데이터 품질 관리

따라서 저장 공간 절약을 위해 원본 데이터를 버리는 것은 우선하지 않는다.

---

## 현재 MVP에서의 적용 범위

Raw/Normalized 분리를 설계 원칙으로 채택하지만, 초기 2026년 샘플 데이터를 사람이 직접 조사하여 입력하는 단계에서는 반드시 완전한 자동 수집 파이프라인까지 구현할 필요는 없다.

즉, 단계적으로 진행할 수 있다.

```text id="r8pkk7"
초기 샘플 데이터
→ 정제된 events 중심으로 구축

자동 수집 도입
→ raw_events에 원본 저장
→ 정제 후 events 반영
```

따라서 Raw Data 분리는 향후 자동 수집 구조를 망가뜨리지 않기 위한 데이터 모델상의 방향으로 결정한다.

---

## 향후 재검토 기준

다음과 같은 요구가 생기면 raw 데이터 모델을 확장한다.

- 자동 크롤러를 운영한다.
- 동일 페이지를 주기적으로 다시 수집한다.
- 행사 정보 변경 이력을 추적한다.
- 수집 시점별 원본 데이터를 비교해야 한다.
- 데이터 정제 실패를 관리해야 한다.
- 재처리 작업을 자동화한다.

이 경우 다음과 같은 구조도 검토할 수 있다.

```text id="o0y4ty"
raw_event_snapshots
├── id
├── source
├── source_url
├── raw_data
├── content_hash
└── collected_at
```

이를 통해 동일 행사 페이지가 시간에 따라 어떻게 변경되었는지도 추적할 수 있다.

---

## 결론

외부에서 수집한 원본 데이터와 서비스에서 사용하는 정제 데이터를 **서로 다른 역할의 데이터로 취급하고 분리한다.**

```text id="9yv93b"
raw_events
→ 외부에서 실제로 수집한 원본 보존
→ 디버깅과 재처리 목적

events
→ 서비스 기준으로 정제된 행사 데이터
→ 검색과 추천에 사용
```

이 구조를 통해 수집 출처의 데이터 형식이 서비스 데이터 모델에 직접 영향을 주지 않도록 하고, 정제 로직이 변경되더라도 원본 데이터를 이용해 다시 처리할 수 있도록 한다.

다만 초기 수동 샘플 데이터 구축 단계에서는 과도한 수집 파이프라인 구현을 요구하지 않고, 자동 수집을 시작할 때 `raw_events` 구조를 본격적으로 적용한다.
