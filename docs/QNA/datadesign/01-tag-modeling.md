# Tag Modeling

## 문제

하나의 행사는 여러 관심 분야에 동시에 속할 수 있다.

예를 들어 하나의 개발 행사가 다음과 같은 태그를 동시에 가질 수 있다.

- AI
- Backend
- Web

따라서 행사와 태그 사이의 관계를 데이터베이스에서 어떻게 표현할지 결정해야 한다.

---

## 고려한 방식

### 1. 문자열로 직접 저장

예:

```text
"AI,Backend,Web"
```

#### 장점

- 구현이 가장 단순하다.
- 별도의 테이블이 필요하지 않다.

#### 단점

- 태그별 검색이 불편하다.
- `"AI"`, `"ai"`처럼 표기가 달라질 수 있다.
- 태그 추가 및 삭제가 번거롭다.
- 중복 태그를 관리하기 어렵다.
- 관계형 데이터베이스의 구조를 충분히 활용하지 못한다.

---

### 2. PostgreSQL 배열로 저장

예:

```sql
tags TEXT[]
```

데이터 예시:

```text
["AI", "Backend", "Web"]
```

#### 장점

- 문자열 방식보다 태그 검색이 쉽다.
- 별도의 관계 테이블 없이 구현할 수 있다.
- 초기 구현이 비교적 단순하다.

#### 단점

- 태그 자체를 독립적인 데이터로 관리하기 어렵다.
- 태그 이름의 중복이나 오타를 통제하기 어렵다.
- 태그에 설명, slug 등의 추가 속성을 붙이기 어렵다.
- 태그 관리 기능이 확장될수록 구조가 복잡해질 수 있다.

---

### 3. N:M 관계로 분리

다음과 같이 세 개의 테이블로 구성한다.

```text
events
  │
  │ 1:N
  ▼
event_tags
  ▲
  │ N:1
  │
tags
```

예:

```text
events
id | title
1  | GIST 개발자 밋업

tags
id | name
1  | AI
2  | Backend
3  | Web

event_tags
event_id | tag_id
1        | 1
1        | 2
1        | 3
```

#### 장점

- 행사 하나에 여러 태그를 자연스럽게 연결할 수 있다.
- 하나의 태그를 여러 행사에서 재사용할 수 있다.
- 태그 이름을 중앙에서 관리할 수 있다.
- 중복 태그를 방지하기 쉽다.
- 태그별 행사 조회가 명확하다.
- 향후 태그에 추가 정보를 넣기 쉽다.
- PostgreSQL의 관계형 구조를 직접 활용할 수 있다.

#### 단점

- `event_tags` 중간 테이블이 추가된다.
- 태그 조회 시 JOIN이 필요하다.
- 배열 방식보다 초기 구조가 약간 복잡하다.

---

## 결정

**행사와 태그를 N:M 관계로 모델링한다.**

다음 세 개의 테이블을 사용한다.

```text
events
tags
event_tags
```

`event_tags`는 행사와 태그를 연결하는 중간 테이블로 사용한다.

---

## 선택 이유

이 서비스에서는 하나의 행사가 여러 관심 분야에 속할 수 있으며, 같은 관심 분야가 여러 행사에서 반복적으로 사용된다.

또한 사용자가 관심 분야를 기준으로 행사를 검색하거나 추천받는 기능이 핵심 기능 중 하나이므로, 태그를 단순한 문자열 값이 아니라 독립적으로 관리 가능한 데이터로 표현하는 것이 적절하다고 판단했다.

PostgreSQL 배열을 사용하면 초기 구현은 더 간단하다. 그러나 태그는 여러 행사에서 반복적으로 재사용되고, 관심 분야 기반 검색과 추천의 핵심 기준으로 사용되므로 MVP 단계에서도 독립 엔티티로 관리할 가치가 충분하다고 판단했다.

따라서 약간의 JOIN 비용과 구조적 복잡성을 감수하고 N:M 관계를 사용한다.

---

## 예상 스키마

```sql
CREATE TABLE tags (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE event_tags (
    event_id BIGINT NOT NULL REFERENCES events(id),
    tag_id BIGINT NOT NULL REFERENCES tags(id),

    PRIMARY KEY (event_id, tag_id)
);
```

`PRIMARY KEY (event_id, tag_id)`를 사용하여 동일한 행사에 동일한 태그가 중복으로 연결되는 것을 방지한다.

---

## 향후 고려사항

현재는 태그 이름만 관리하지만, 필요할 경우 `tags` 테이블에 다음과 같은 속성을 추가할 수 있다.

```text
slug
display_name
description
category
created_at
```

또한 태그의 종류가 많아질 경우 상위 분류와 세부 태그를 구분하는 구조도 추후 검토할 수 있다.
