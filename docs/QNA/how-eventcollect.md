# 행사 데이터는 어떻게 수집하는 것이 좋을까?

## 질문

행사 추천 서비스를 만들 때, 행사 데이터를 어떤 방식으로 수집하는 것이 좋을까?

예를 들어 다음과 같은 방법을 생각할 수 있다.

> 스케줄러를 두고 일정 시간마다 AI API를 호출해서 웹에서 행사를 검색하도록 하면 되지 않을까?  
> 직접 Google 검색 결과를 크롤링하는 것보다 이 방식이 낫지 않을까?

---

# 1. AI API를 행사 수집기로 사용하는 방법

가장 단순하게 생각하면 스케줄러가 일정 주기로 AI API를 호출하도록 만들 수 있다.

예를 들어 다음과 같은 요청을 보내는 방식이다.

```text
2026년 9월에 열리는
AI, 게임 개발 관련 행사들을 찾아줘.

행사명, 날짜, 장소, 신청 링크를
JSON 형식으로 반환해줘.
```

그러면 시스템은 다음과 같은 구조가 된다.

```text
Scheduler
    ↓
AI API
    ↓
웹 검색
    ↓
행사 목록
    ↓
Database
```

구현 자체는 상당히 간단해 보인다.

하지만 서비스의 메인 데이터 수집 방식으로 사용하기에는 몇 가지 문제가 있다.

---

# 2. 왜 AI 검색을 메인 수집 방식으로 사용하면 안 되는가?

## 2.1 어떤 행사가 누락됐는지 알 수 없다

가장 큰 문제는 **검색 결과의 완전성을 보장할 수 없다는 것**이다.

예를 들어 어제 AI가 다음 행사들을 반환했다고 하자.

```text
A
B
C
```

오늘 같은 조건으로 다시 검색했는데 다음과 같이 반환될 수도 있다.

```text
B
D
```

그러면 시스템 입장에서는 `A`, `C`가 왜 사라졌는지 알 수 없다.

가능한 원인은 여러 가지다.

```text
A 행사가 취소됨

C 행사가 종료됨

검색 결과에서 일시적으로 누락됨

AI가 이번에는 다른 검색 결과를 선택함
```

따라서 단순히

```text
오늘 검색에서 안 나옴
→ 행사 삭제
```

라고 처리할 수도 없다.

---

## 2.2 동일한 요청이라도 결과가 달라질 수 있다

AI 기반 검색은 같은 요청을 반복한다고 해서 항상 동일한 URL이나 동일한 행사 목록을 반환하는 것이 아니다.

즉,

```text
Input
↓
Output
```

관계가 완전히 결정적이지 않다.

이 특성은 새로운 정보를 발견하는 데에는 장점이 있지만, 데이터베이스를 지속적으로 유지하는 수집 시스템에서는 문제가 될 수 있다.

---

## 2.3 데이터 변경 여부를 추적하기 어렵다

행사 정보는 자주 변경될 수 있다.

예를 들어 다음 정보들이 수정될 수 있다.

```text
행사 날짜

행사 장소

신청 마감일

모집 상태

행사 취소 여부
```

AI에게 매번 다시 검색을 요청하는 방식에서는

> 기존 행사 페이지의 내용이 실제로 변경된 것인지

를 정확하게 추적하기 어렵다.

---

## 2.4 출처 관리가 어려워진다

서비스에서 행사 정보의 신뢰성을 확보하려면 출처를 관리해야 한다.

예를 들어 다음과 같은 정보가 필요하다.

```text
행사 출처

원본 URL

마지막 확인 시각

마지막 수정 시각
```

AI 검색 결과만 받아 DB에 넣으면 이런 수집 이력을 체계적으로 관리하기 어렵다.

---

## 2.5 비용이 불필요하게 증가할 수 있다

매번 AI에게 웹 검색과 행사 정보 추출을 모두 맡기면 많은 토큰과 API 호출이 필요하다.

하지만 실제 행사 페이지 대부분은 매일 변경되지 않는다.

따라서 같은 내용을 매번 AI에게 다시 분석시키는 것은 낭비가 될 수 있다.

---

# 3. Google 검색 결과를 직접 크롤링하는 방법은?

다른 방법으로 Google 검색 페이지 자체를 직접 크롤링하는 것도 생각할 수 있다.

예를 들면 다음과 같다.

```text
google.com/search?q=AI+세미나+2026
```

결과 HTML을 가져와 행사 URL들을 추출하는 것이다.

하지만 이 방식도 메인 수집 방식으로 사용하기에는 적합하지 않다.

---

# 4. 왜 Google 검색 결과 크롤링도 좋지 않은가?

## 4.1 검색 결과 HTML 구조에 의존한다

Google 검색 결과 페이지의 HTML 구조가 변경되면 크롤러도 같이 수정해야 한다.

즉,

```text
Google HTML 변경
↓
Crawler 오류
↓
행사 수집 중단
```

과 같은 문제가 발생할 수 있다.

---

## 4.2 검색 서비스 자체에 지나치게 종속된다

서비스의 핵심 데이터 파이프라인이 특정 검색엔진의 결과 페이지 구조에 의존하게 된다.

따라서 검색 방식이 변경되거나 접근이 제한될 경우 전체 서비스가 영향을 받을 수 있다.

---

## 4.3 검색 결과는 원본 데이터가 아니다

Google은 어디까지나 행사 페이지를 찾아주는 검색 서비스이다.

실제 행사 정보의 원본은 다음과 같은 사이트에 존재한다.

```text
공식 행사 홈페이지

이벤터스

온오프믹스

기업 홈페이지

대학 홈페이지

기관 행사 페이지
```

따라서 검색 결과 자체를 계속 크롤링하기보다 검색을 통해 원본 페이지를 발견한 뒤, 해당 원본을 직접 관리하는 것이 더 안정적이다.

---

# 5. 권장 방식

행사 수집과 AI의 역할을 분리하는 것이 좋다.

전체 구조는 다음과 같다.

```text
                    Scheduler
                        │
            ┌───────────┼───────────┐
            ↓           ↓           ↓
          API/RSS    직접 크롤러    Search
            │           │      새로운 행사 발견
            └───────────┼───────────┘
                        ↓
                    Raw Event
                        ↓
               Structured Parser
                        ↓
                파싱 실패 여부
                   ↓        ↓
                  성공      실패
                   │        │
                   │      AI API
                   │        │
                   └────┬───┘
                        ↓
               Normalized Event
                        ↓
                  Validation
                        ↓
                 Deduplication
                        ↓
                  PostgreSQL
```

---

# 6. AI가 해야 할 역할

AI 자체가 인터넷에서 행사를 찾는 역할을 담당하기보다는,

> 이미 가져온 행사 페이지의 내용을 구조화하는 역할

을 담당하는 것이 적절하다.

예를 들어 크롤러가 다음과 같은 텍스트를 가져왔다고 하자.

```text
제7회 개발자 모임

올해는 생성형 인공지능이 개발 환경에
어떤 변화를 일으키는지 논의합니다.

행사는 9월 19일 토요일 오후 2시부터
판교 XX타워에서 진행됩니다.

사전 등록은 9월 16일까지입니다.
```

이 내용을 AI에게 넘기고 다음과 같이 요청할 수 있다.

```text
다음 행사 페이지에서 정보를 추출하라.

{
  "title": string,
  "startAt": string | null,
  "endAt": string | null,
  "registrationDeadline": string | null,
  "venue": string | null,
  "region": string | null,
  "categories": string[]
}
```

그러면 다음과 같은 데이터를 얻을 수 있다.

```json
{
  "title": "제7회 개발자 모임",
  "startAt": "2026-09-19T14:00:00+09:00",
  "endAt": null,
  "registrationDeadline": "2026-09-16T23:59:59+09:00",
  "venue": "판교 XX타워",
  "region": "경기",
  "categories": [
    "Development",
    "Generative AI"
  ]
}
```

즉 AI는 **Crawler가 아니라 Extractor 또는 Normalizer** 역할을 한다.

---

# 7. 모든 페이지를 AI에게 보낼 필요도 없다

페이지 정보는 다음과 같은 우선순위로 처리한다.

```text
페이지 수집
    ↓
JSON-LD와 같은 구조화 데이터가 있는가?
    ↓
YES → 직접 파싱
    ↓
NO
    ↓
사이트별 HTML Parser로 처리 가능한가?
    ↓
YES → 직접 파싱
    ↓
NO
    ↓
AI API 사용
```

AI는 최후의 fallback으로 사용하는 것이다.

---

# 8. JSON-LD가 있다면 AI가 필요하지 않다

일부 행사 사이트에서는 다음과 같은 구조화 데이터를 제공한다.

```html
<script type="application/ld+json">
{
  "@type": "Event",
  "name": "AI Developer Conference",
  "startDate": "2026-09-12T14:00:00"
}
</script>
```

이미 기계가 읽을 수 있는 형식으로 데이터가 제공되므로 AI API를 호출할 필요가 없다.

그대로 파싱하면 된다.

---

# 9. 변경되지 않은 페이지는 다시 처리하지 않는다

페이지 내용을 해시로 저장하면 불필요한 작업도 줄일 수 있다.

예를 들어 다음 값을 저장한다.

```text
source_url
raw_html
content_hash
fetched_at
```

페이지를 다시 가져온 뒤 SHA-256 등의 hash를 계산한다.

```text
어제 hash

abcdef...

오늘 hash

abcdef...
```

값이 같다면 페이지 내용이 변경되지 않은 것이다.

따라서

```text
content_hash 동일
↓
변경 없음
↓
AI 호출 X
↓
DB Update X
```

로 처리할 수 있다.

---

# 10. 그렇다면 검색은 어디에서 사용할까?

검색 기능 자체는 여전히 유용하다.

다만 역할을

> 행사 수집

이 아니라

> 새로운 행사 또는 새로운 Source 발견

으로 제한한다.

예를 들어 주기적으로 다음과 같은 검색을 할 수 있다.

```text
"AI 세미나" 2026 9월

"게임 개발 행사" 2026

"개발자 밋업" 2026

"해커톤" 2026 9월
```

검색 결과에서 기존 DB에 존재하지 않는 URL을 발견한다.

```text
Search
↓
새로운 URL 발견
↓
candidate_urls
```

그다음 해당 URL을 일반적인 수집 파이프라인에 넣는다.

```text
candidate_urls
↓
Page Fetch
↓
Parser
↓
AI Extractor
↓
Validation
↓
DB
```

---

# 11. Source를 중심으로 관리한다

서비스에서 지속적으로 행사 정보를 가져올 사이트를 `Source`로 관리한다.

예를 들면 다음과 같다.

```text
sources

1. 이벤터스
2. 온오프믹스
3. 특정 개발자 커뮤니티
4. 기업 기술 행사 페이지
5. 대학 행사 페이지
6. 공공기관 행사 페이지
```

각 Source는 다음과 같은 정보를 가질 수 있다.

```text
id

name

base_url

type

last_crawled_at

enabled
```

그리고 각 Source에 대응하는 Collector를 만든다.

```text
collectors/

eventus.ts
onoffmix.ts
university.ts
company.ts
```

---

# 12. 스케줄러의 역할

스케줄러는 AI에게 행사를 찾으라고 요청하는 역할이 아니라

> 등록된 Source들을 일정 주기로 다시 확인하는 역할

을 담당한다.

예:

```text
Scheduler
↓
활성화된 Source 조회
↓
각 Collector 실행
↓
새 페이지 확인
↓
변경 여부 확인
↓
Parsing
↓
DB Update
```

---

# 13. 수집 주기

모든 페이지를 같은 주기로 확인할 필요는 없다.

예를 들면 다음과 같이 설정할 수 있다.

| 대상 | 수집 주기 |
|---|---:|
| 행사 목록 페이지 | 6~12시간 |
| 한 달 이상 남은 행사 | 하루 1회 |
| 7일 이내 행사 | 6~12시간 |
| 신청 마감 임박 행사 | 3~6시간 |
| 종료된 행사 | 추가 확인 중단 |
| 새로운 행사 Search | 하루~주 1회 |

초기에는 단순하게 하루 1~2회로 시작하고 나중에 조정해도 된다.

# 14. 최종 구조

권장하는 전체 데이터 파이프라인은 다음과 같다.

```text
                         API / RSS
                             │
                             │
Scheduler ──────── Known Source Crawler
                             │
                             │
                   Search Discovery
                    새로운 URL 탐색
                             │
                             ▼
                       Candidate URL
                             │
                             ▼
                         Fetch Page
                             │
              ┌──────────────┴──────────────┐
              │                             │
        Structured Parser              AI Extractor
        JSON-LD / Parser               fallback
              │                             │
              └──────────────┬──────────────┘
                             ▼
                         Validation
                             ▼
                       Deduplication
                             ▼
                        PostgreSQL
                             ▼
                  Search / Recommend API
                             ▼
                         Frontend
```

# 결론

다음과 같은 구조는 피하는 것이 좋다.

```text
Scheduler
↓
AI에게 웹 검색 요청
↓
AI가 행사 목록 반환
↓
바로 DB 저장
```

검색 누락이나 결과 변화 여부를 추적하기 어렵고, 데이터의 출처와 최신성을 관리하기 어렵기 때문이다.

대신 다음과 같이 역할을 분리한다.

```text
API / RSS / Crawler
→ 행사 데이터 수집

Search
→ 새로운 행사 및 Source 발견

AI
→ 행사 페이지 내용 추출 및 정규화

Scheduler
→ 주기적인 수집 및 갱신

Database
→ 행사 상태와 변경 이력 관리
```

즉 이 서비스에서 AI의 핵심 역할은

> **행사를 찾아오는 것**

보다는

> **찾아온 행사 페이지를 이해해서 정형 데이터로 만드는 것**

에 두는 것이 적절하다.

결과적으로 프로젝트의 핵심도 단순한 웹 크롤러가 아니라

```text
수집
→ 정규화
→ 검증
→ 중복 제거
→ 저장
→ 검색
→ 추천
```

으로 이어지는 **행사 데이터 파이프라인**이 된다.
